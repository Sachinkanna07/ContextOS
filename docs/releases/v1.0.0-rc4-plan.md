# RC4 frontier provider implementation plan

## Current architecture

RC3 keeps memory retrieval, selection, compilation, routing, provider dispatch, and telemetry in `ContextOSModelService`. Providers implement the existing `ModelProvider` protocol. `ModelDiscovery` already bounds and caches independent inventories. The daemon registers a fake, Ollama, and one localhost OpenAI-compatible provider; `LLMConfig` is legacy and sparse. `ModelRequest` carries compiled context to each adapter. The CLI lacks `ask` and provider status.

## API contracts checked 2026-10-04

* [OpenAI Responses](https://developers.openai.com/api/reference/cli/resources/responses/methods/create): `POST https://api.openai.com/v1/responses`, Bearer API key; `model`, `input` and `instructions`, `max_output_tokens`, optional model-supported `temperature`. Response `output[]` contains message `content[]` with `output_text`; `status`, `incomplete_details.reason`, `usage.input_tokens`, `usage.output_tokens`, `usage.total_tokens`, and `id` identify result and usage. [Models](https://platform.openai.com/docs/api-reference/models/object?lang=curl): `GET /v1/models` exposes IDs but no dependable text or temperature capability metadata. Default temperature will be omitted; explicit temperature can be sent and a provider rejection remains a safe typed error.
* [Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create): `POST https://api.anthropic.com/v1/messages`, `anthropic-version: 2023-06-01`, API key authentication (current Bearer and legacy x-api-key supported); top-level `system`, `messages`, `max_tokens`, optional supported `temperature`. Response `content[]` has text and non-text blocks; only text is public answer. `stop_reason`, `usage.input_tokens`, `usage.output_tokens`, `id`; cache input token fields may contribute to provider usage. [Models](https://platform.claude.com/docs/en/api/models/list): `GET /v1/models`, pagination and metadata including context and output limits.
* [Gemini Interactions](https://ai.google.dev/gemini-api/docs/interactions-overview): recommended since June 2026 for new integrations; stateless `POST https://generativelanguage.googleapis.com/v1/interactions`, `x-goog-api-key`, `model`, `input`, `system_instruction`, `generation_config.max_output_tokens`, optional supported temperature, and `store:false`. REST response contains `steps[]` with `model_output.content[]` text, `status`, `usage.total_input_tokens`, `usage.total_output_tokens`, `usage.total_tokens`, `id`. Do not expose thought steps. [Models](https://ai.google.dev/api/models): `GET /v1beta/models`, paginated, with generation actions and token limit metadata. The older `generateContent` remains supported but is no longer preferred for new integrations.

All adapters map only fixed HTTP status and recognized protocol states to safe typed errors. No raw response bodies, headers, URLs, prompts, or keys go into exceptions, logs, or telemetry. Unknown capabilities remain false. Native and compatible remote providers stay unregistered unless explicitly configured and credentials are present. Explicit remote selection is allowed; automatic fallback requires a separate remote opt-in.

## Implementation sequence

1. Add structured validated provider configuration with legacy `llm` compatibility, safe URL and env-name handling, named compatible endpoints, and daemon registration.
2. Add shared safe HTTP/error/token helpers and native OpenAI, Anthropic, and Gemini adapters; preserve compiled context and conservative capability metadata.
3. Gate implicit remote routing, add CLI ask and provider status, validate API inputs, and avoid printing context by default.
4. Add protocol, security, routing, discovery, memory invariance, and CLI tests; run required static/full/clean-checkout/install/review gates.
5. Version RC4, tag exact clean commit, and publish canonical tagged bytes only after all release gates pass.
